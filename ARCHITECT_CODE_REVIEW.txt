2. АДЕКВАТНІСТЬ АРХІТЕКТУРИ
--------------------------------------------------------------------------------

Стиль: **Layered Modular Monolith** (не повний Hexagonal).

  Controllers → Services → Engine/Model + Repositories
                ↘ Clients (MarketData)

Адекватність для учбової CEX: **ТАК**.
- Один процес, H2, in-memory OrderBook — правильний trade-off для демо.
- Розділення MatchingEngine (pure calc) vs OrderService (orchestration) — сильне рішення.
- Не тягнути мікросервіси / Kafka / CQRS — правильно (біль немає).

Що віддаємо: HA, горизонтальне масштабування matching, durable order book,
строгий audit на всіх шляхах (раніше seedDemoBalances обходив audit — виправлено).

Опції (якби росли далі):
  A) Залишити моноліт + PostgreSQL          ← рекомендую наступним кроком
  B) Винести matching у окремий процес      ← лише при реальному multi-node
  C) Event sourcing ордерів                 ← overkill зараз

5. CODE REVIEW FINDINGS
--------------------------------------------------------------------------------

### 🔴 Blocker
(немає підтверджених blocker після cleanup + green tests)

### 🟠 Major
1. Partial LIMIT: після часткового fill `adjustReservedAmount` був порожнім stub
   (видалено виклик). Поведінка: зайвий reserve може лишатись до cancel/full fill.
   Де: OrderService (був ~418). Потрібен ОКНИЙ алгоритм зменшення reserve = filled.
2. Single-node consistency: OrderBook у RAM; crash між commit і afterCommit рідкісний,
   але можливий drift до restore.
3. Security: /ws-exchange/** і /h2-console/** permitAll — ок для demo, не для prod.
4. Приватний fin-core-lib — рев’юер без доступу не збере проєкт.

### 🟡 Minor
1. OrderService GOD-METHOD зона (~480 рядків): submit + OCO + trigger + cancel.
2. MatchingManager.init: не-LIMIT → trigger pool (MARKET pending теоретично туди потрапить).
3. Oracle @Scheduled під час тестів → ERROR-логи без fail.
4. open-in-view=true warning.
5. Fee rates захардкоджені в FeeService.

### 💡 Idea
- CircuitBreaker на MDS (Sprint 3).
- PostgreSQL profile.
- Розрізати OrderService на OrderPlacement / OrderTrigger / OrderCancel.

### 👍 Удачно
- Lock поза TX + TransactionTemplate + afterCommit sync.
- MatchingEngine без side-effects на book.
- OCO + trigger activation після commit.
- DTO на межі API; JWT tokenVersion на reset.
