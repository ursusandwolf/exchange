# Security Overview

Этот документ описывает текущую модель безопасности проекта `exchange`: как работает регистрация, логин, JWT, доступ к пользовательским данным и какие ограничения нужно учитывать.

## 1. Границы доверия

- Backend считается источником истины для аутентификации, авторизации и финансового состояния.
- Frontend хранит только сессионный JWT, username и userId для удобства UI.
- Все критичные проверки выполняются на backend, а не в браузере.

## 2. Поток регистрации и логина

### Registration

1. Клиент отправляет `POST /api/auth/register`.
2. Backend валидирует `username`, `email` и `password`.
3. `AccountService` проверяет уникальность `username` и `email`.
4. Пароль хэшируется через `BCryptPasswordEncoder`.
5. Создаётся пользователь и возвращается `AuthResponse` с JWT, `userId`, `username` и флагом `admin`.

### Login

1. Клиент отправляет `POST /api/auth/login`.
2. `AuthenticationManager` проверяет учетные данные через `DaoAuthenticationProvider`.
3. При успешной аутентификации backend загружает пользователя и выдает JWT.
4. При неуспешной аутентификации возвращается `401 Unauthorized`.

### Password reset

1. Клиент отправляет `POST /api/auth/password-reset/request` с email.
2. Backend генерирует одноразовый reset token, сохраняет только его hash и отправляет ссылку на email.
3. Клиент открывает страницу сброса пароля и отправляет `POST /api/auth/password-reset/confirm`.
4. Backend проверяет срок действия и одноразовость токена.
5. При успешном сбросе пароль хэшируется заново, а `tokenVersion` пользователя увеличивается, чтобы отозвать старые JWT.
6. На auth endpoints действует rate limiting, чтобы снизить риск brute-force и массового abuse.

## 3. JWT-модель

- Токен подписывается HMAC SHA-256.
- Секрет берется из `app.security.jwt.secret`.
- В токен кладется `sub=userId`, `username` и `tokenVersion`.
- Срок жизни токена сейчас составляет 24 часа.

### Что важно

- Секрет не должен храниться в коде.
- Секрет нужно задавать через `JWT_SECRET` или другой защищенный механизм конфигурации.
- При компрометации секрета нужно ротировать токены.
- При сбросе пароля старые JWT становятся невалидными за счет увеличения `tokenVersion`.

## 4. Доступ к защищенным эндпоинтам

Защищенные маршруты требуют заголовок:

```http
Authorization: Bearer <jwt>
```

Поток проверки:

1. `JwtAuthenticationFilter` извлекает токен из заголовка.
2. Токен валидируется через `JwtService`.
3. `UserDetailsService` загружает пользователя по `username`.
4. Если токен валиден, создается `Authentication` в `SecurityContext`.

### Защищенные зоны

- `/api/user/**`
- `/api/orders/**`
- Пользовательские эндпоинты требуют `ROLE_USER` или `ROLE_ADMIN`
- `/api/admin/**` только для `ROLE_ADMIN`
- Все прочие эндпоинты, кроме явно разрешенных в `SecurityConfig`

## 5. Пользовательские данные

`UserController` возвращает:

- портфель пользователя (`/api/user/portfolio`)
- историю операций (`/api/user/history`)

Backend определяет пользователя через authenticated principal. Пользователь не может выбрать чужой `userId` в запросе и получить чужой портфель напрямую.

## 6. Хранение данных на клиенте

Frontend использует `zustand` с `persist`, поэтому в `localStorage` сохраняются:

- `token`
- `username`
- `userId`

### Ограничения этого подхода

- Любой JavaScript, работающий в origin приложения, может прочитать токен.
- XSS в приложении приведет к компрометации сессии.
- Это приемлемо только для учебного проекта или внутреннего стенда.

## 7. Кеширование и переключение пользователя

React Query кеширует результаты запросов пользователя.

Чтобы не показывать данные прошлой сессии:

- кеш очищается при logout,
- ключи пользовательских запросов включают `userId`.

Это важно для сценария, когда один браузер используется для нескольких аккаунтов подряд.

## 8. Обработка ошибок

### Сейчас

- Ошибки валидации возвращают `400 Bad Request`.
- Ошибки аутентификации возвращают `401 Unauthorized`.
- При превышении лимита попыток возвращается `429 Too Many Requests`.
- Невалидные JWT игнорируются фильтром и приводят к отказу уже на уровне security chain.
- Password reset request не раскрывает, существует ли email в системе.
- Password reset confirm возвращает generic ошибки для просроченного или уже использованного токена.

### Что не делать

- Не возвращать stack trace наружу.
- Не раскрывать, существует ли конкретный пользователь, в сообщениях логина.
- Не использовать разные сообщения для "user not found" и "bad password" в публичном API.

## 9. Основные риски текущей версии

1. `localStorage` для JWT.
2. Нет refresh token flow.
3. Rate limiting есть, но он in-memory и не переживает рестарт приложения.
4. Нет MFA.
5. Нет централизованной ротации JWT secrets.
6. Нет device/session management.
7. Email-based password reset зависит от корректной mail-конфигурации в окружении.

## 10. Рекомендации для следующего этапа

1. Вынести JWT secret только в secret manager или защищенный env.
2. Вынести rate limiting в распределенное хранилище, если приложение будет масштабироваться горизонтально.
3. Перейти с `localStorage` на httpOnly cookie, если нужен более строгий security baseline.
4. Добавить refresh token и отзыв сессий.
5. Ввести audit log для входа, выхода и неуспешных попыток авторизации.
6. Добавить integration tests на:
   - bad credentials -> 401,
   - expired token -> 401,
   - access to `/api/user/**` without token -> 401.
7. При необходимости добавить MFA и device/session management поверх текущего password reset flow.

## 11. Текущая конфигурация

- Stateless JWT auth.
- CSRF выключен, потому что используются bearer tokens.
- Session state не хранится на backend.
- Все решения по правам доступа принимаются на backend.
